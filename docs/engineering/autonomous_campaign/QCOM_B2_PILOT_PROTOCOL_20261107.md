# QCOM B2 isolated pilot protocol — conditional, no device action

The only current runnable device mode in [qcom_b2_pilot.py](../../../tools/release/qcom_b2_pilot.py) is read-only `--inspect` (default) or `--plan`. `--execute` exits 2 with `NO_GO_EXECUTION_DISABLED`. The Windows authenticated controller may transport or inspect this script in a separately authorized session; Ubuntu must not SSH to comma. Transport that writes a script is itself a device write and remains blocked by the same gates. A read-only stdin invocation may be used only after the Windows controller has verified command quoting, script hash, host identity and its own authorization. No unvalidated string is interpolated into a remote shell. The run ID accepts exactly 16 lowercase hex characters; no broad destination or installed-source path parameter exists.

## Proof required before implementing an execution path

1. Operator-owned controller provides an authenticated, fresh, continuously checked stationary/parked, ignition-off, disengaged proof from **both** `pandaStates` and `carState`. Subscription failure, sparse samples, stale heartbeat, a state transition, or disagreement aborts before staging and kills the isolated compiler process group during activity. A 30-second cadence fixture is a minimum screening check, not enough by itself to prove operational safety.
2. Independently verify installed known-good `/data/openpilot` SHA `a969e5e60debe4d7d5f5f6ec2935f5a97f2bd0d1`, no active control or Panda process, AGNOS 19.9, GPU driver/userspace, actual CPU and GPU sensors, working `/usr/local/venv/bin/python3`, SCons 4.10.1, numpy 2.5.1, capnpc, taskset CPUs 0–7, and exact handoff/checkout hashes. Any missing proof is NO-GO. The script's simple read-only Git HEAD display does not establish these facts.
3. Demonstrate a device-enforced, aggregate hard quota for **all** files in the one pilot directory, including source staging, Git metadata, cache, TMPDIR, HOME, outputs and logs. Proposed experiment ceiling is 512 MiB and memory ceiling is 512 MiB, each requiring proof of enforceability and no impact on active driving services. Do not infer an aggregate bound from `ulimit -f`, SCons cache size, or sampled `df`. Require current `/data` free >= 2 GiB + quota before creating the directory and continuously enforce >=2 GiB actual reserve. If the exact checkout cannot fit under the quota, stop without compilation. Source size, archive duplication and scratch must be counted once, at simultaneous peak.
4. Prove an independent watchdog that fails closed on missed heartbeat, ignition, engagement, control/Panda process, thermal rise (actual sensor only), OOM, GPU error, disk reserve, timeout and operator abort. Set a short explicit experiment timeout and retain time-stamped CPU/GPU temperatures, MemAvailable, cgroup memory high-water, filesystem quota use, `/data` free, compiler exit status and any GPU fault log. A periodic monitor cannot catch every instantaneous spike, so the hard quota and memory boundary are prerequisites.
5. After all gates pass, create exactly one new isolated `/data/mvl-builds/<source SHA>/pilot-<run-id>` with no symlink components. Stage a verified Git checkout there; no writes under `/data/openpilot`, installed caches, `/tmp`, Panda, ECU or CAN. Run exactly the one stock SCons target in the plan, with `SKIP_TINYGRAD_COMPILE` absent. Preserve the output and its SHA only if the compiler exits zero and all monitoring remains valid. A valid artifact from this experiment is resource evidence only, not S12 PASS. If a stage or compile fails, stop and leave evidence for authorized, path-bounded cleanup. A cleanup implementation must prove exact path ownership and avoid following symlinks before deletion; no such implementation is active yet.

## Current decision and handoff

No aggregate quota, live-state subscriber/watchdog, memory isolation, or cleanup implementation has been validated on AGNOS 19.9. **NO-GO.** The Windows controller must treat `--execute` exit 2 as an intentional hold, not bypass it with a manual shell command. A later reviewed code change and focused tests are required before the owner's conditional pilot authorization can become executable. Even a successful one-warp pilot would leave five outputs, full product build, package and device/release tests open. No install, launch, reboot, Panda/ECU/CAN change or vehicle control change is within this protocol.
